| 私聊链接不再"每 5 分钟主动重发" | 维护者要求取消那条主动重发（报告 #5）：从前 `tick()` 里有一件独立的事——每轮按"时间窗变没变"给收过链接的主人 / 白名单管理员重发一条私聊（`modules/manager-link.js` 的 `refreshManagerLinks` / `refreshPlan` / `resendOne` + `REFRESH_TEXT`），并顺带撤回上一条。**去掉的理由**：① **它是多余的**——作废旧链完全靠编辑器那一侧的时间窗（只认当期与上一窗口），重发并不是"让旧链失效"的必要条件；② **它是骚扰**——窗口一变就给每个管理员推一条私聊，人不在电脑前时这些消息只堆在那儿；③ **它要维护一份定时状态**（`data/manager-link.json` 的窗口比对、逐人失败重试、移出名单者的记录剔除），而这份状态与"链接本身"没有任何关系。现在口径是**只在本人发 `#排队` 时给一次**：链接带的是**那一刻的当期窗口**，**5 分钟窗口过期即失效**，要新的就再发一次 `#排队`。**删掉**：`apps/queue.js` 的 `tick()` 里那两行（调用 + 注释）与 import 里已无用的 `refreshManagerLinks` 并同步 `init()` / `tick()` / `afterSend` 的注释（"五件事"→四件、"不会进 5 分钟换新名单"→"这一次没记进状态文件"）。`modules/manager-link.js` 里只服务主动重发的 `refreshManagerLinks`、纯函数 `refreshPlan`、`resendOne`（含撤回那一段）与 `REFRESH_TEXT` 一并删掉，连带清掉只为它们存在的 import（`log` / `windowEpoch` / `windowedEditorUrl` / `managerQqs`）；**保留** `#排队` 仍在用的 `dmSender` / `recordManagerLink` / `DM_FAILED_TEXT` 与 `readLinkState` / `writeLinkState`（记录落点与格式没变）。**没有新增任何定时任务**（那条 tick 的任务数、cron 与其余四件事一字未动；`init()` 里的注册判据保持原样）。**回归**：`test/manager-link.test.mjs` 两处依赖"tick 主动发链"的断言块改成新口径——【4】把"窗口变了 ⇒ 给每个管理员各发一条新的"改成 **tick 窗口变没变都一条不发**，紧随其后的两条不再遍历 tick 发出来的空数组，而是**改指本人发 `#排队` 那一刻的那一条私聊**（先钉住各收过两条、再逐条核"带的是当期窗口 `win`、用那一刻的时间戳 `verifyWindow` 验得过、与状态文件记的窗口一致"），并新增"tick 一轮都没动状态文件里的窗口"；【5】改成"名单变了 tick 也不给任何人发链 + 状态文件一个字没变"（删掉了依赖刷新逻辑存在的"移出名单者记录被剔除"）。注释与文档（`README.md` / `docs/开发说明.md` / `editor/README.md` / `test/README.md` / `components/fill-entry.js` / `components/config.js` / `model/whitelist.js` 的相关注释）同步成"只在本人发 `#排队` 时给一次，5 分钟窗口过期即失效"；`AGENTS.md` 未动。**如实说明**：本轮没做变异验证（维护者要求只跑必需套件），两条新断言的"能红"路径是推演出来的——把 `refreshManagerLinks` 加回 `tick()` 会让【4】【5】的 `fresh.length === 0` 直接红。`docs/历史沿革.md` 本行即说明。 |
| 手机 / QQ 内置浏览器打开链接读不到数据（设备令牌不再只靠 cookie） | 维护者贴图报的：主人链接在手机与 PC 的 QQ 内置浏览器里打开，页面能出来、数据全读不到，提示 `读取失败：Unexpected token '<', "<!doctype "… is not valid JSON`。**根因链**（代码里逐条核过）：页面自己发的 `/api/*` **不带时间窗**——`editor.html` 的 `withToken()` 只回填 `k/u/s/a`，地址栏那串 `w/ws` 在打开时就被 `history.replaceState` 清掉了；而服务端对"有身份、没窗口"的请求只认**认领过这条链接的那台设备**（`editor.mjs` 的「链接的时间窗」第 4 条 + `claims.js` 的 `resolve()`），那台设备的唯一凭据是 **cookie** `abyss_editor_device`。QQ / 微信的内置浏览器常把 cookie 当第三方挡掉、或无痕不落盘，于是页面能渲染（打开那一发窗口有效、认领也成功），后续每个 `/api/*` 都撞上 **410 的失效页（HTML）**，前端 `res.json()` 就报出那句 `Unexpected token '<'`。**修法（两条一起，维护者选的 1+2；不动身份 / 认领键 / 角色 / 窗口判据）**：① **设备令牌支持请求头**——`editor/claims.js` 新增 `DEVICE_HEADER`（`x-abyss-device`）：`deviceOf()` **请求头优先、cookie 兜底**（两处共用同一个 `parseToken`，只认 `<32 位十六进制设备号>.<HMAC>`）；`setDevice()` 在种/续 cookie 的同时把**同一个令牌**回一份响应头；认领那一段（`editor.mjs`）把令牌存进请求状态（`state.deviceToken`），首页路由把模板里的 `__DEVICE__` 换成它（没认领就是空串）。页面把注入的令牌存 localStorage，之后每次请求用 `x-abyss-device` 带上，并从任何响应的同名头里收下新令牌（续期 / 换设备跟得上）。令牌只证明"这台设备认领过这条链接"、不含身份，签名绑"哪条链接 + 哪个身份"，所以换个身份 / 换条链接都验不过。② **窗口引导**——页面把地址栏的 `w/ws` 也收进 sessionStorage，**只在还没有设备令牌时**带上它们（这一发才走得通"首次认领"、把令牌换回来）；已经有令牌就不带窗口（带过期窗口反而会把好用的会话顶掉），万一这一发因窗口过期被 **410**，**去掉窗口重试一次**（cookie 正常的浏览器照旧走第①条，不给它们引入回归）。③ 顺手把"接口返回的不是 JSON"换成能用的提示（`jsonOf()`：先 `text()` 再自己解析，发现是 HTML 就说"链接多半已失效或被中转页挡住，回群里重发 #排队"，而不是把 `Unexpected token '<'` 甩给用户）；页面里 13 处 `fetch(withToken(...))` 统一改走 `apiFetch()`。**回归**：`editor/test/link-claim.test.mjs` 新增一组 6 条（无 cookie 的设备打开链接 ⇒
