# 协作与开发约定

> 日志与注释、Git 与提交摘要、工作流程、授权粒度、越权防线、子代理、需先确认、禁止、验收、入库范围、协作分工。
> 本册是 `AGENTS.md` 第五节（约定）、第六节（硬约束）、第七节（工作流程）的全文版；两处冲突以 `AGENTS.md` 为准。

## 日志、版本号、注释

- 日志一律 `logger?.info` / `logger?.warn` / `logger?.error`，**不用 `logger?.debug`**。
- 版本号走 `components/pluginVersion.js`，导出 `pluginVersion`（读本插件 `package.json`）与 `yunzaiName` / `yunzaiVersion`
  （读 bot 根 `package.json`；**框架名按 bot 根包名判**——`name` 含 `trss` 是 `TRSS-Yunzai`，其余是 `Yunzai-Bot`，
  与 Axiu-Plugin / ProfileImg-Plugin 的 `pluginVersion.js` 同一条判据）；HTML 模板底部统一显示
  `Created By {yunzaiName} {yunzaiVersion} & {PluginName} {pluginVersion}`。**具体范围**：四张出图（总览 / 单榜 / 主播列表 / 帮助）
  都要有那行（模板里的 `.ver`），并且**各自的纯文本兜底末尾也要有**（出图关掉或发不出去时走的就是它）；由调用方把
  `versionFooter(PLUGIN_NAME)` 传进 `renderMenuImg` / `renderQueueImg` / `renderAnchorsImg` / `renderHelpImg`（`version` 形参）。三条群通知
  （完成 / 开榜 / 月末催办）**不带**——它们是通知，不是查询输出。
- 版本号怎么升见 `AGENTS.md` 第五节第 9 条：**平时只动后两位**（修 bug 动末位、加能力动次末位），只有大方向的大型更新
  （编辑器整体重构、仓库代码重构与精简）才动首位；改完同一轮在 `CHANGELOG.md` 顶部加一节。
- 保留原有注释风格（`/** */` 块注释、语句旁 `//`）；函数写 JSDoc（功能 / 输入 / 输出）；对边界条件与设计决策写注释，
  对"调了什么 API"不写注释。注释**不记录单次 bug 修复过程**（不写"修复了…的 bug""之前是…现在改为…"）。
- **历史沿革不写在代码里**：注释只讲"现在是什么、为什么这样设计、边界在哪"；代码与文档里**不出现**"以前是…／已经删掉…／
  老配置／旧键／不再…"这类**沿革说明**——它们一律记进 [`历史沿革.md`](历史沿革.md) 对应的分册。配置模板
  （`config/config.yaml.example`）只描述当前键与当前语义，**不解释"某个键为什么没了"**。
- **改动落盘时同步写对应文档**：改到目录结构 / 配置键 / 命令 / 接口 / 部署口径，必须同一轮更新 `README.md`、
  [`开发说明.md`](开发说明.md)、`config/config.yaml.example`、`editor/README.md` 里对应的那份，**不留到最后补**；
  结构性变更同时往历史沿革分册追加一行（只追加，不改写历史行）。文档改完跑 `node tools/doc-check.mjs`。

## 开发与部署

- **两份源码仓库，各自开发**：两位维护者各持一份源码仓库（不是共享目录，也不做软链接——框架要求插件真实位于
  `<bot根>/plugins/` 下）；各自在自己那份上改代码、跑测试、提交、推送。
- **运行实例由部署方维护**：插件运行目录只由更新指令（框架的 `#更新`）从远端拉取，**不接受任何手工拷贝**——手工同步会
  制造未提交改动，下一次更新必然报本地改动冲突。
- **验证顺序**：改到影响运行行为的代码，先在源码仓库跑离线套件（`pnpm test`）；需要真机验证时，由部署方按自己的部署流程
  同步到运行实例；DSH **不直接改运行实例目录里的文件**。
- **加日志验证后必须还原**：临时调试日志（`logger?.info('[模块名-DEBUG] ' + JSON.stringify(data))`）在验证通过后一律删除，
  再提交。

## Git 与提交摘要

- **不执行任何 git 操作**：不 `git add` / `commit` / `push` / `merge` / `checkout` / `clone` / `pull`。
- 改动完成后给提交摘要：单行标题 `prefix: 中文描述`（`feat:` / `fix:` / `refactor:` / `chore:` / `docs:`），详细列表每行 `- `
  一项；**代码与仓库内文档（`AGENTS.md` / `README.md` / `docs/` / 各 README）都算改动**，一并列入。
- **摘要是一切仓库改动的交付前提**：任何对仓库的改动——代码 / 测试 / 文档 / 配置模板——在交付时都必须同时给出提交摘要；
  **没有摘要视为未交付**，不能以"改动很小""只动了一个字""已经跑过测试"为由省掉。摘要只反映本次 diff 的真实内容。
- **摘要必须"跟进"**：它是**每一轮改动结束时的固定收尾**，跟着最新一轮改动走——每一轮（哪怕只改一行）交付时都要重新给一次
  **当前这一轮**的摘要；**只写这一轮的新改动**，不重复上方已经给过的摘要；要跨轮**合并**成一条，只有维护者明确说"合并"时
  才做。若某轮开始时发现上一轮漏了摘要，**先补上一条能对齐当前 diff 的摘要**再继续干活——把"漏摘要"当成与"测试没过"同级
  的缺陷。

## 仓库里不留真实指纹

本仓库会公开发布，维护者自己的**域名、IP、QQ 号、群号、本机绝对路径**一律不进仓库：它们对任何功能都不是必需品，却能被人
"顺着域名 / 号码"摸到服务器与账号。

- **示例一律用占位**：编辑器地址写 `https://example.com/queue`（RFC 2606 保留域名，保证不会撞到真实站点）；QQ / 群号写假号
  （如 `1000000001` / `100000002`），并且**保持位数一致**（10 位 QQ 就写 10 位假号）——免得踩到任何长度敏感的逻辑。
- **适用范围**：`README.md` / `docs/` / 各 README、代码注释、配置模板与参考文件（`defSet/config.yaml`、
  `config/config.yaml.example`）、锅巴的引导文案与 placeholder、**回归套件夹具**、渲染模板（`resources/**`）。
- **例外（本来就要留的）**：规范署名——`footer.html` 默认值与页脚署名里的两位维护者名字、GitHub 链接；上游作者的 GitHub
  句柄；以及**示例数据里的主播名**（那是插件的示例内容，不是地址）。真正要藏的是"能定位到机器或账号"的东西。
- **不入库的工作文件不受此限**：`.dsh/` 下的审查提示词之类保留真实环境信息更有用。
- 新增文档 / 示例 / 夹具时照此写；发现仓库里已经有真实指纹，**同一轮改掉**，并在历史沿革分册追一行。

## 工作流程（先调查，再设计，后实现）

1. **只读调查**：量出现状与目标规范的实际差距，形成**差距清单**（逐条：现状 → 规范要求 → 影响）。此阶段不写任何文件。
2. **出方案**：针对差距清单给出对齐方案，含改动范围、文件级影响、风险点、以及**明确不做什么**。技术选型可自行决定并说明
   理由，不必逐项征询。
3. **等确认**：方案得到维护者确认后才写实现代码。确认前不落盘。
4. **实施**：按确认的范围改，**不顺手改无关代码**，不夹带重构。
5. **验证**：跑 `test/`（若有）或给出可复现的验证方式；实测失败就说失败，跳过就说跳过。

> 套件的跑法与耗时见 [`测试.md`](测试.md)，逐套清单见 [`../test/README.md`](../test/README.md)。

**授权粒度（这条踩过坑，必须守住）**

- **一次授权 = 一步**。维护者认可某一步，只授权**那一步**；做完立刻停下汇报，**等下一次明确授权**才能动下一步。
- **"定方案"不等于"开始执行"**：让 DSH 出方案、把方案写下来、确认方案内容，都只到"方案已定"为止；宁可多问一句"现在开始
  执行第 N 步吗"，也不要顺手往下做。
- **批量 / 连续执行不成立**：即使方案里写了"步骤 1、2、3"，也不代表 1 做完可以接着做 2。
- **不自行判断"顺理成章"**：改动互为前提、共享同一批文件、只差一处 import 之类，都不是可以自行推进的理由。
- 越界的代价要认：已经把改动落盘了，也**先停下来报告越界**，由维护者决定是保留、回退还是重做——不要靠"再补做一步"把问题
  糊过去。

**越权防线（执行时的硬约束）**

以下行为一律算越权；一旦发生，立刻停下报告，由维护者决定保留、回退还是重做：

1. **不得把"全做完 / 都改了吧 / 下一步 / 你看着办"解读成批量授权**：`下一步` 只授权**当前清单里的那一步**；要连做必须逐步
   拿到明确同意。
2. **不得一边做一边扩大范围**：已确认范围之外的**文件与行为**一律不碰；发现"顺手也该改"的，先停下问。
3. **不得碰运行实例或环境**：不改 `<bot根>/plugins/abyss-queue` 里被跟踪的文件、不手工拷贝代码进去；**为验证去改仓库外或
   运行期文件（`.gitignore`、宿主 `plugins/other/**`、`renderers/**`、启动脚本等）同样禁止**——验证只在仓库内或系统临时目录
   里做，且用完清理。
4. **不得先落盘后请示**：只读调查、出方案、写方案都不落盘；未获明确同意前不写实现代码。已经落盘了也要立刻停下报告越界，
   不要用后续动作掩盖。
5. **改 `AGENTS.md` 不必先问**：`AGENTS.md` 与实际不符、或本轮改动新增 / 改变了某条口径时，**直接改**，并在提交摘要里列明改了
   哪几节——它与代码同级、一同评审提交。只有两件事仍要先说一声：**重写整节 / 删掉整条既有约定**，以及**改动维护者已经确认过
   的行为口径**（那等于改需求）。历史沿革分册照旧**只追加**，永不改写历史行。

**越权后的处置**：停止 → 报告"改了哪些文件、原计划是什么、越了哪一条" → 等维护者裁决；**不得**自行回退、不得自行补做、
不得继续下一步。

功能行为的原则：**对齐规范 ≠ 改行为**。只有当某处行为本身违反框架契约、且维护者已确认，才允许动行为。

**子代理（subagent）使用约束**

- **非必要不派子代理**。它只适合「与当前会话上下文无关、能自包含描述」的一次性工作（只读调查、互不重叠文件上的并行小改）。
- **下列情况一律自己动手**：改动要贴着既有约定与注释风格；需要先读多个文件才能判断；需要连续验证（改—跑—改）；本会话已
  反复出现的小修小补；改动涉及权限、表结构或安全口径。
- 派出去时必须一次给全硬约束：不许改断言语义、不许扩大范围、不许碰运行实例目录与线上服务、不执行任何 git 命令、临时文件
  只放系统临时目录；并要求**简短回报**（改了哪些文件、跑了什么、结果、疑虑）。
- 子代理的产出**一律按「未经复核」对待**：给维护者的结论与提交摘要由会话自己出；子代理擅自落盘的文件要如实报告并交维护者
  处置。

## 需先与维护者确认才能做的事

- 目录改名（补 `-plugin` 后缀）
- 单入口 ↔ 目录遍历模式切换
- 大面积文件移动、重命名、删除
- 删除上游自带文件（含上游 `AGENTS.md` 的处理）
- 引入新依赖（`sharp`、`puppeteer`、`yaml` 等）
- 修改对外的命令正则 / 触发词 / 权限等级
- 表结构口径（列识别、状态取值、行归属规则）与任何对群友可见的行为变更
- 修改本文件（两位维护者都读它，改它等于改共同约定）

> 其中「命令正则 / 触发词 / 权限等级 / 表结构口径 / 群友可见的行为」属**对群友可见**的改动，需要**两位维护者都同意**；
> 其余项经在场维护者同意即可。

## 明确禁止

- 执行 git 操作（见上「Git 与提交摘要」）
- **改动没带提交摘要就交付**：任何代码 / 测试 / 文档 / 配置模板改动，交付时必须同时给出 `prefix: 中文描述` + `- ` 列表的摘要；
  **没有摘要视为未交付**
- 依据上游文件恢复或改写上游文件的流程与规范
- 擅自加功能、改行为、做与规范对齐无关的重构
- 用 `logger?.debug`
- 用 `Object.keys(mod)[0]` 之类的方式挑插件 class
- 解析 `defSet/config.yaml` 过滤 `${变量}` 作为配置兜底
- **修改框架 / 环境文件来让本插件工作**：`plugins/other/update.js`、`renderers/**`、启动脚本等**都不是本仓库的东西**，不得要求
  或引导用户去打「本地补丁」（既违反部署口径，也会在框架升级时被覆盖）。插件功能只能落在本仓库内（`apps/` / `components/` /
  `model/` / `modules/` / `editor/` / `guoba/` / `resources/`）；缺什么就**换个不需要框架改动的做法**，或如实说明限制
- 在运行实例目录（`<bot根>/plugins/abyss-queue`）里直接改被跟踪的文件
- 往仓库（会被发布的内容）里写维护者真实的域名 / IP / QQ 号 / 群号 / 本机绝对路径——示例一律用占位
- 在工作目录之外另起会话根（开发会话 cwd 必须让项目级指令与 skills 生效，否则它们会静默失效）

## 验收标准

一次改动被视为完成，需同时满足：

1. 目录结构、命名、入口加载方式与状况一致（或偏差项已获维护者确认并记录在方案里）。
2. 配置为三层结构，`config.yaml` 可缺省回退到 `.example`，注释不被写坏。
3. 日志等级、版本号来源、注释风格统一；版本号已按约定升、`CHANGELOG.md` 顶部有对应一节。
4. `pnpm test` 可跑：通过则全绿，缺前置则打印「跳过」并 `exit 0`；改过文档的加跑 `node tools/doc-check.mjs`。
5. 给出提交摘要（`prefix: 中文描述` + `- ` 列表），未执行任何 git 操作。

## 协作约定（两人共同维护）

1. **分工口径**：本仓库有两份源码仓库、一个运行实例；运行实例由部署方维护，代码经远端同步。改代码前先看清自己改的是哪一份，
   改动只在源码仓库里落。
2. **改动前对齐**：动全仓库基线里的东西（目录、入口、命名、配置三层、部署口径）或"需双确认"项，先在会话里说清"改什么、
   为什么、影响面"，另一位维护者确认后再落。
3. **同步冲突的由来**：运行实例只接受更新指令的改动。若某次更新报「本地改动会被覆盖」，先看 `node test/check-deploy.mjs` 的
   输出，再决定是丢弃本地改动还是提交；**不要**用强制对齐去覆盖别人未提交的现场改动。
4. **文档跟着行为走**：命令 / 配置键 / 表结构口径变了，同步更新 `README.md`、`config/config.yaml.example`、对应 `docs/` 页面
   与文档站页面（文档站不入库）。
5. **本文件的改动同样要留痕**：改 `AGENTS.md` **不必先问**，但要在提交摘要里列明改了哪一节——它是两个人共用的唯一约定来源。
   历史沿革分册里记"为什么改"，本文件里只放**当前口径**。
6. **不替对方拍板**：拿不准归属的口径，问；不要"先按自己的理解改一版再让别人接受"。
