# 回归套件（结构、纪律与跑法）

> 套件结构、前置跳过、超时、端口、断言纪律，以及跑法与耗时。原 `AGENTS.md` §3.7 + §四 的「效率约束」。
> 2026-11 从 `AGENTS.md` 按模块拆出，正文逐字未改；章节号已去掉，旧编号见 [`旧编号对照.md`](旧编号对照.md)。

## 回归套件 `test/`

- **套件数（实测，2026-11 本机）**：`test/` 43 套 + `editor/test/` 40 套 = **83 套**；`node test/run.mjs --list` 会逐行列出这 83 个相对路径，改动前先看清单，别盲跑。
  - **干净克隆上按设计整套跳过的是 `test/editor-host.test.mjs` 一套**（前置是 `data/queue.xlsx`，而 `data/` 不入库）——本机 `data/` 里没有那张表时同样跳过，于是典型结果是 **82 通过 / 1 跳过 / 0 失败**（跳过不算失败，也**不算通过**）。
- 结构：`<主题>.test.mjs` + `_helper.mjs`（路径/前置/断言/框架全局桩）+ `run.mjs`（入口）+ `fixtures/`。
- `pnpm test` = `node test/run.mjs`，**任意 cwd 可跑**，不启动 bot。
- **缺前置一律打印「跳过」并 `exit 0`**，不得直接失败。
- 临时产物写 `test/.test-tmp/`（gitignore）。
- **每套有超时**：`test/run.mjs` 默认 120 秒、`ABYSS_TEST_TIMEOUT_MS` 可调（不是正数直接退 2）；
  超时按**失败**计（"没跑完"不等于"通过"）并杀掉**整棵进程树**——套件会起真实子进程（编辑器、
  宿主的 HTTP 服务），吊住一个就让 `pnpm test` 永远不返回，而 Windows 上 `child.kill()` 只杀直接
  子进程，留下的孤儿会继续占着那张表、把后面的套件一起带红。
- **套件要的依赖必须写进 `package.json`**：`express` 只有 `test/editor-host.test.mjs` 用
  （要真摆出框架那四个 body parser），所以列在 `devDependencies`。借宿主上层的 `node_modules`
  跑到只能算巧合，干净克隆上就是 `ERR_MODULE_NOT_FOUND`。
- **断言不许绑本地目录名**：检出目录被改名（GitHub 下 ZIP 会解成 `abyss-queue-main`）不该让套件
  变红；要比就比仓库内的正式名（`package.json` 的 `name`），它才是面板 key 与部署目录的约定。
- **端口一律现要、不许写死**：起编辑器进程的套件用 `freePort()`（`test/_helper.mjs`，编辑器侧经
  `editor/test/harness.mjs` 取），拿到的值原样传 `--port`。固定端口只要撞上（两套并发跑、本机留着个
  没退干净的编辑器）就以 `fetch failed` / "编辑器没起来"变红，看不出原因；`harness.startEditor()`
  的"起不来换一个端口重试"照旧保留（绑 `0` 问到重新绑上有极小窗口）。
- **套件里"保存一行"的用例：只提交真正要改的字段，行号一律现查**（2026-10-13 定，来源：第六轮排查报告 +
  本机对照复现）：`/api/data` 下发的 `status` 是**展示值**（表里写着字面「本人已完成」的行会被换成该行的
  群昵称），整行照抄回 `/api/save` 就等于把它改成昵称——那是一次**真改动**，会触发「立刻整理」把行挪走，
  于是后面所有按行号的引用都指错人（症状是"校验未通过：昵称与表格第 N 行重复"）。**只提交 `note` 也不保险**：
  服务端会给漏传字段补上表里的现值，再走一遍"本人已完成 → 群昵称"，所以凡是要动 `status` 的用例得先按
  "完成情况 ≠ 自身群昵称"挑行。稳妥写法：`values: { note: "…" }` 这种**部分字段** + 每次写之前按
  **昵称**或**QQ 绑定**现查行号（`rowOfNick()` / `rowByNick()` / `myRowNow()`；本人那一行在
  `editor/test/editor.test.mjs` 中途会被改成新群名片，不能拿开场快照里的昵称找），"要还原成什么"也从现表读。
  另外：**别在用例里就地写坏入库文件**（`test/guoba.test.mjs` 的坏模板用例已改成临时替换 `fs.readFileSync`）——
  两份全量并发跑时，共享文件会被对方读到坏内容。
- 套件只测**对外行为与契约**：不为内部实现细节导出函数，不写只覆盖死代码的断言（`test/` 内不出现仅测试用的导出）。
- **自定义的 `check` / `must` 必须"真的跑断言体"**：`test/_helper.mjs` 的 `createChecker().check(name, fn)` 是标准写法（回调抛错即失败、async 回调会被等）。
  早年有 8 个 `editor/test/` 套件各自写了一份 `const check = (name, ok, detail) => { if (ok) ✅ }`——**回调永远是"真值"**，
  于是 `check("名字", () => {...})` / `await check("名字", async () => {...})` 那批用例只印 ✅、**一条断言都没执行**
  （2026-10 自查抓到：把 `editor/util.js` 的原子写改回直接写目标，那条新断言照样打 ✅）。自写断言器只有一条纪律：
  **`typeof ok === "function"` 就调用它、同步/异步都等结果**（现在的 8 份已统一成这个形状）。
  自查手法：临时把被测实现改坏（变异），那一条必须变红；不变红就是断言没跑。

## 跑法与耗时

**效率约束（每条都对应实测，不要靠感觉）**

依据：2026-11 本机一次 `node test/run.mjs` **全量 83 套**（本机无 `data/queue.xlsx` 时 `editor-host` 跳过，典型结果 82 通过 / 1 跳过 / 0 失败）。
拆开量（同一个 runner，单套逐跑）：`editor\test\anchor-add` 2.81 s、`test\workbook` 2.52 s、
`editor\test\editor` 2.47 s、`editor\test\quota-guard` 1.72 s、`editor\test\changes` 1.45 s、
`editor\test\live-refresh` 1.33 s、`editor\test\link-latest` 1.26 s、`editor\test\link-claim` 1.07 s、
`test\guoba` 1.09 s、
`editor\test\save-conflict` 0.86 s、`test\workflow` 0.56 s、`test\init` 0.18 s、
`test\editor-host`（跳过）0.20 s、`editor\test\client-state` 0.12 s；`node test/run.mjs editor`（`editor\test\` 40 套 +
跳过的 `editor-host`）**约 65 s**，`test\` 那 43 套合计十几秒。

- **大头是"每套一个 node 进程"的固定开销，不是 xlsx 解析**：裸 `node -e 0` 约 23 ms，再静态 import
  `jszip` + `yaml` + `express` 到约 144 ms（express 占 ~94 ms、`yaml` ~42 ms、`jszip` ~49 ms，见各自单测）；
  83 套各起一个进程，光是"起进程 + 加载依赖"就是秒级起步。xlsx 侧只有 `workbook` 一套真做逐行比对，
  2.52 s 里还含同样的启动费；`.NET` 那条（`test/verify-xlsx.ps1`）**根本不在这次全量里**，
  它是手工复核用的独立脚本（§3.7 / `test/README.md`），不要把它算成套件耗时的来源。
- **第二块是"起 HTTP 服务 + 等端口就绪"**：`editor/test/` 里许多套件真的起编辑器进程（`harness.startEditor()`
  起在临时目录里），每套要等子进程 listen + `/healthz` 才开跑；这解释了
  62.1 s 为什么远大于那几张最大的文件之和。
- **反复跑全量本身才是最大的一笔**：4 次全量 ≈ 4.7 分钟；单套只跑受影响的 1–3 秒——"改一行跑一遍全量"
  是这套东西里最贵的习惯。
- 因此：**迭代只跑受影响的套件**（`node test/run.mjs <文件名片段>`，见下），全量留给"一轮改动收尾"那一次；
  需要跨改动的回归证据时，**一次全量同时当计时与回归**即可，不要为了"再看看"反复全量。
- **`--list` 先看清单，别盲跑**：`node test/run.mjs --list` 只列 83 个套件路径、约 60 ms。
- **筛选参数是位置参数、不是 `--filter=`**：`node test/run.mjs --filter=workbook` 里的 `--filter=…`
  被运行器**忽略**，等于又跑了一遍全量（实测连跑 4 次才看出来）；正确写法是
  `node test/run.mjs test/workbook.test.mjs`、`node test/run.mjs editor/test`——按 `--list` 印出来的
  相对路径**片段**匹配（`--list` 一律用 `/`；Windows 下用 `\` 也能命中，但照清单抄更稳）。
- **知道每套 120 秒的上限**：超过按失败计并杀掉整棵进程树（见 §3.7）；真撞上先看是不是编辑器没退干净。
- **一次命令行的固定开销也要算进迭代成本**：本机起一个 `powershell -NoProfile` ≈ 0.6 s、`cmd /c` ≈ 6 ms、
  裸 `node -e 0` ≈ 23 ms。所以"来回很多次、每次一条命令"的代价主要是 shell 启动，能合并的探查/命令合并执行。
